# Audit, 3 September 2026

On 3 September 2026 I audited this repository against its own claims: every tool description and error string the server sends to a model, the README and `docs/DESIGN.md`, and the write paths in `src/drive.ts` and `src/tools.ts`, driven by a fake `drive_v3` client. The audit found nine issues, a second pass found eleven more introduced or left behind by the first round of fixes, and a third round on 4 September 2026 closed the last three; this file records all of them with what was wrong and what changed.

## What was wrong and what changed

### 1. Binary writes

`update_file_content` accepted a string and passed it to `files.update` with the file's own MIME type, and nothing anywhere decoded base64. The error text in `replace_in_file` told a model to recover by reading the file as base64 and calling `update_file_content` with the result, which stored the ASCII of the base64 as the file's bytes and reported success. All four write tools now refuse a file whose content did not decode to text, and the README and `docs/DESIGN.md` say that writing binary content back is unsupported.

### 2. Revision order and truncation

`listRevisions` returned one page of `revisions.list` unsorted and unpaged, while the tool description said "newest first". Drive's `revisions.list` takes no ordering parameter and pages at 1000. The function now walks every page, sorts on `modifiedTime`, and slices the newest `pageSize`.

### 3. The concurrency guard

`docs/DESIGN.md` called the guard "the same shape as an HTTP `If-Match` / `ETag` exchange". The token is compared against a separate `files.get` and is never sent to Google, so a write landing between the check and the update is not caught. The design doc now states the difference and the window, and the README says the write is refused if the file changed before the write is issued.

### 4. Comments

The README's opening sentence and its comparison table listed comments as preserved. A native Doc is edited by exporting the whole body to markdown and re-importing the whole body, which orphans anchored comments. The opening sentence now claims the file ID, sharing settings and revision history, the table row is qualified, and the word was dropped from the `update_file_content` description.

### 5. Slides

`importMimeFor` had no Slides case and fell through to `text/plain`, which Drive does not accept as a presentation import. `writeFile` now refuses a Slides file by name before any API call, and the import table in `docs/DESIGN.md` reads `refused` for that row.

### 6. Fabricated deltas

`readFile` leaves `content` undefined for a binary file, so `summarizeChange(before.content ?? '', content)` measured every delta against an empty string. The binary refusal added in issue 1 now throws before that line, so the summary only runs on content that was read as text. The refusal still downloads the file to classify it.

### 7. Timestamp granularity

`docs/DESIGN.md` said `modifiedTime` has one-second granularity. Drive returns RFC 3339 with milliseconds, and the repository's own fixtures use `2026-01-01T00:00:00.000Z`. The sentence now says millisecond resolution.

### 8. The unknown token

`revisionToken` returns the string `unknown` when Drive supplies neither `headRevisionId` nor `modifiedTime`. A read and a later write both landing on `unknown` compared equal, and the write proceeded unguarded. `writeFile` now throws when a caller supplies a token and the current token is `unknown`.

### 9. The authorize flow

`scripts/authorize.mjs` prints the Google consent URL for the user to open and listens on `http://localhost:4181/oauth2callback` for the redirect. The README said it opens a consent flow on localhost:4181. The README now describes what the script does.

### R2-1. The unguardable file

The first version of the `REVISION_UNKNOWN` message said to re-read the file and try again, which returns the same two missing fields. The message now says a re-read will not change anything, that `update_file_content` without `expectedRevisionToken` is the only way to write such a file, and that the three targeted tools cannot write it at all.

### R2-2. The pagination loop

The loop added for issue 2 followed `nextPageToken` with no bound. It now stops after 50 pages or on a repeated token, and `list_revisions` appends a truncation notice when either happens.

### R2-3. Other native types

The Slides refusal was one MIME constant, so a Site, a Drawing, a Form or a Jamboard still reached `files.update` as `text/plain`. `writeFile` now refuses on an allow-list of Docs and Sheets, with a separate message for Slides.

### R2-4. The status code

The Slides message asserted that Drive returns a 400. Nothing in the repository establishes that code. The message now says the write cannot succeed and names no status.

### R2-5. The comments qualifier

The first qualifier said anchored comments are orphaned "since the whole body is re-imported", which is also true of an uploaded file. The row now reads that comments are preserved on the file object and that anchored comments may be orphaned by a full-content rewrite.

### R2-6. Sorting

The first fix reversed the array, which is correct only while Drive returns revisions oldest first. The list is now sorted on the `modifiedTime` field the query already requests.

### R2-7. The heading

The README body was narrowed to a client-side check while the heading above it still read "Concurrent edits are refused". The heading now carries the qualification.

### R2-8. Error precedence

A guarded write to a Slides deck with a stale token returned the conflict message, which tells a model to re-read and write again, and every retry ended at the Slides refusal. The native-type check now runs before the revision check.

### R2-9. Message consistency

`append_to_file` and `prepend_to_file` used a shorter binary refusal that named no recovery. All four now end with the same two sentences.

### R2-10. The force option

The conflict message said not to retry with force unless the caller has said to discard the other edit. No tool has a `force` parameter. The message now says the server has no force or override option, and `docs/DESIGN.md` quotes the new text.

### R2-11. Test wording

A test assertion string read "writing a binary file must fail, not report success". It now reads "a binary file must be refused".

## Closed in the third round

### B-1. The `update_file_content` description

The description added in the first round said "Text files and native Google files only." Slides, Sites, Drawings, Forms and Jamboards are native Google files and every one of them is refused by `writeFile`, whose `WRITABLE_NATIVE_TYPES` holds Docs and Sheets alone. The description now reads "Text files, Google Docs, and Google Sheets only", and says every other native Google type is refused.

### B-2. The server instructions

`src/index.ts` told the client to "re-read and merge rather than forcing" after a conflict, which implies an option the server does not have and which `src/errors.ts` says does not exist. The instructions now end "re-read and merge. This server has no force option."

### B-3. Control bytes in a test file

`test/drive.test.mjs` contained three raw control bytes, `0x00 0x01 0x02`, inside a string literal used as binary test content. Node parsed it and the suite passed, but git classified the file as binary, so its diffs did not render in review or on GitHub. The literal is now `'\x00\x01\x02'`, the file holds no byte below 0x09, and git counts it as 470 lines of text.

## Checked and found correct

I registered the compiled tools against a fake `drive_v3` client and called the handlers the server actually exposes.

No write path creates and trashes a file. `files.create` appears once in `src/`, in `createFile`, which is reached only by `create_file`. There is no call to `files.delete`, `files.copy`, or any trash operation anywhere in `src/` or `scripts/`. A `replace_in_file` edit issued one `files.update` against the same file ID and zero `files.create` calls.

The file ID is preserved. Every write funnels into `writeFile`, which calls `drive.files.update({ fileId, media })` with the ID it was given.

Sharing is preserved. Nothing in `src/` touches the `permissions` collection, and `files.update` is called with a media body and a `fields` string only.

Revision history is preserved. `files.update` with a media body appends a revision, and nothing in the repository deletes or modifies a revision.

The refusals hold, with zero `files.update` calls and the target bytes unchanged in each case. A PDF is refused by all four write tools, including a guarded `update_file_content` call carrying the correct token, an empty-string overwrite, and a `replaceAll` replacement. A MIME type carrying a charset parameter, an uppercased type, `application/octet-stream` and `image/png` are all refused. Slides, Sites, Drawings, Forms and Jamboards are refused by all four write tools, including a Slides deck with a matching token and one with a stale token. Docs and Sheets still write, at `text/markdown` and `text/csv`. A file with no `headRevisionId` and no `modifiedTime` is refused by all four tools when a token is supplied, and the escape the error message names, `update_file_content` with no token, does write. A stale token is refused with zero `files.update` calls and the file left as it was.

`list_revisions` returns newest first from an oldest-first API response and from a shuffled one, and a newer revision sitting on a later page still appears at `pageSize: 1`. A server that repeats a `nextPageToken` stops after two calls, an endless sequence of distinct tokens stops at 50, and both cases append the truncation notice.

The tool surface is nine tools: `read_file`, `get_file_metadata`, `search_files`, `list_revisions`, `update_file_content`, `replace_in_file`, `append_to_file`, `prepend_to_file`, `create_file`. `scripts/verify.mjs` asserts that count and the README documents all nine.

`npm ci` installed 162 packages against the committed lockfile, `npm run build` and `npm run typecheck` are clean, and `npm test` is 67 passing, 0 failing, 0 skipped.

## What remains unverifiable

Everything that needs a live Google account is unverified here. `npm run verify` was not run, so nothing in this file confirms that Drive appends a revision on `files.update`, that sharing survives a write, that comments survive a write on an uploaded file, that anchored comments are orphaned on a native Doc, that `headRevisionId` is absent on native files, or that Drive rejects a plain-text import for a presentation. The Slides and native-type refusals are the server's own policy, so they hold regardless, but the reason given for the Slides refusal is a claim about Drive's import formats that no test in this repository establishes. The concurrency window between the `files.get` check and the `files.update` write is a property of the Drive API, which offers no precondition on `files.update`, and it cannot be closed from the client. The fake `drive_v3` client used here returns what the code expects Drive to return, which is the same limitation `npm run verify` exists to cover.
